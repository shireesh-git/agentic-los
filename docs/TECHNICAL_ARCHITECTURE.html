Agentic Corporate LOS: technical architecture

The LOS runs a corporate loan from prospect to disbursement. Multi-agent graphs populate it, and people verify and decide. Its core is a credit-intelligence (CAM) engine. Work that can run in parallel does, a single writer keeps state consistent, and every value carries provenance through the populate → verify → lock cycle.

Summary

What an architect needs to know in four boxes.

AGENTIC

Agents populate

Agents for document intake, due diligence, the credit case, reconciliation and the critic propose values for every workspace. Each proposal carries its source, evidence and confidence.

PARALLEL

One DAG scheduler

AgentGraph runs every agent graph. It handles declared dependencies, fan-out per document, check, domain or section, a bounded pool, a per-provider LLM cap and a deterministic join.

GOVERNED

People verify and decide

A field registry sets verification policy. Proposals land in a verify queue, and decided values lock. No agent can take a workflow or credit decision.

LEAN

POC footprint

One FastAPI process, SQLite, in-process threads, a filesystem document store and a pluggable LLM. There is no new infrastructure; production swaps are listed in Path to production.

Architecture principles

These hold across every component and are enforced in code, not by convention.

Deterministic figures, AI reasoning. Plain-code engines compute ratios, policy, stress tests and RAROC. Models read documents, draft text and propose values. They never compute a credit figure.
Parallel by default, dependencies declared. Nodes declare requires and waits_for. Anything without a dependency runs concurrently. Code order never implies ordering.
Single writer. Agents return proposals and never write the application. One merge step, under a per-application lock, writes once and emits one audit event.
Provenance on every value. Each value records its source (document and page, external, engine, record or AI), its evidence and its confidence. Missing data is shown as unavailable; it is never invented.
Human decisions are never overwritten. A confirmed or overridden value is locked. A later, different proposal becomes a conflict.
Agents propose, people decide. No agent, tool or copilot has a path to submit, approve, return, reject, sanction or disburse.
Configuration over code. The workflow (stages, steps, roles, SLAs, actions, decision fields) and the field registry (domains, policies, thresholds) live in YAML.
Degrade, don't fail. A failed branch is marked unavailable and the graph continues. With no LLM (mock), every feature falls back to deterministic behaviour.

Execution model: AgentGraph

One scheduler runs every agent graph: the CAM pipeline, intake, preparation and population.

Nodes

A node is an agent or tool with a run function. It declares requires (must succeed first) and waits_for (use the result if present). It belongs to a lane for progress display.

Fan-out and join

A fan-out node expands at run time into N children (per document, check, domain or CAM section). They are joined by item key, not completion order, so output never depends on timing.

Bounded concurrency

A global pool (agentic.max_workers, 16) plus a per-provider LLM semaphore (max_parallel_llm) avoids rate-limit storms. Deterministic tools are not throttled.

Failure isolation

A failed branch marks its output unavailable and dependants that only waits_for it continue. A failure in a requires chain skips the dependants. Critical nodes raise.

Events

Every node emits start and result events with lane, status and duration. The UI shows the lanes live, and the run log is kept with the preparation event.

Measured

Each run reports duration and the peak number of nodes running at once, so parallelism is observable rather than assumed.

graph = AgentGraph([
    Node("credit_case", run=credit_case),
    Node("checks", fan_out=lambda ctx: check_ids, run_item=run_api_check),     # one child per check
], name="appraisal-prep", on_start=lane_running, on_result=lane_done)
run = graph.run({})            # → run.data("credit_case"), run.data("checks"), run.log(), run.max_concurrency

Populate → Verify → Lock

The field store is the contract between agents and people. Every agent-filled value is a FieldValue in the application. The field registry (config/los_fields.yaml) says where each domain is verified and how.

"fields": {
  "cma.financials.revenue.FY2025": {
    "domain": "cma",
    "status": "proposed",          // proposed | confirmed | overridden
                                   // | conflict | unavailable
    "value": 312.4,
    "proposal": {
      "value": 312.4, "confidence": 0.95,
      "provenance": "source", "resolver": "reconciliation",
      "sources": [{"kind": "document", "document":
                   "audited_financials_fy2025.pdf", "page": 1}],
      "target": "cma.subjects[...]", "issues": []
    },
    "decision": null,              // who, when, value, reason
    "history": [ ... ]             // bounded (history_limit)
  }
}

Merge rules (single writer)

  • Proposals merge under a per-application lock in one write and one event.
  • A decided value (confirmed or overridden) is never overwritten.
  • A new proposal that differs from a decided value becomes a conflict. The person chooses keep (with a reason) or accepts the new value.
  • Where two resolvers propose a field, registry order decides, unless the first has no value.
  • Materialise writes verified values into the governed workspaces (CMA, securities and others) by target path. It records agent ownership and never replaces a person's own entry.
  • Mirroring works in reverse: saving a pre-filled form (consent, tranche, beneficiary) confirms equal values (compared numerically) and records different ones as overrides.

Field lifecycle

proposed→ confirmed/ overridden→ different re-proposal → conflict→ keep / accept → decided· reopen → proposed

Verification policy

PolicyRule
Pre-tickConfidence ≥ pretick_confidence (0.85), no critic issues and policy bulk → pre-ticked for one bulk confirm. Nothing is auto-accepted.
must_verifyConfirmed individually and never in a bulk confirm. Applies to risk grade, system recommendation, internal rating, decision, structure, deviations, KYC and watch-list status, legal name, requested amount and all drafted narrative.
Default confidence by provenancesource 0.95 · calculated 0.95 · external 0.90 · derived 0.90 · template 0.70 · ai 0.60 · synthetic_demo 0.40 (never pre-ticked) · unavailable 0
Where verifiedEach domain lists its verify_at steps. For example, sourcing is verified at PS; CMA, rating and pricing at the Risk Makers; parties, securities, exposure and narrative at the IP and AP Notes; post-sanction and disbursement at their makers.
Who may verifyOnly the holder of the step where the domain is verified. Reviewers, checkers and committees are read-only.

Feedback loop: overrides re-flow to the engines

A correction is not just a display edit. Overridden CMA and collateral values become verified overrides on a copy of the company record, and the credit case re-runs.

The original engine value is retained alongside the override, and extraction skips verified keys so a re-read cannot undo a person's figure. The POC limits re-runs to CMA and collateral inputs; other domains change the record without re-running the engines.

LLM layer

All model calls go through src/core/llm_provider.py. Nothing else talks to a model API.

Pluggable providers

NVIDIA NIM (default), Anthropic, Gemini, OpenAI, Azure, Ollama (local) and mock, selected by active_provider. Model IDs, the vision flag and the max_parallel_llm cap are set per provider.

Structured output

generate_structured(schema) prompts for JSON, validates it against the schema and retries with the errors. It works the same way on every provider. A failure raises StructuredOutputError.

Vision

images=[{mime, data}] on every provider. The intake agent sends scanned pages only when the provider declares vision: true; otherwise the page is reported as unread.

Concurrency cap

A bounded semaphore per provider, installed on every provider subclass, wraps each call. This makes parallel graphs safe against rate limits.

Grounding

Any AI text that can quote numbers passes the figure check against its source facts. Extracted values must appear verbatim on the cited page.

Offline mode

mock raises LLMUnavailableError for structured calls. Every feature falls back to deterministic behaviour and says so in the UI. Tests run this way.

Data & runtime

Persistence

  • los_applications: one JSON document per application, holding workflow position, workspaces, fields, decisions, deferrals and sanctions.
  • los_events: the append-only audit trail; the MIS and agent metrics are computed from it.
  • case_runs, companies: credit cases (each application pins its run_id) and the borrower catalogue.
  • Document store: storage/documents/{entity}/{category}/, versioned. Extraction results are cached by content hash.

Runtime

  • One FastAPI/Uvicorn process. Preparation and assessment jobs run on in-process threads, and their job state is held in memory.
  • Sessions are in memory; sign-in is a demo picker.
  • Container: Docker image with code and config; storage, output and DB are mounted volumes. Cloud Run deployment script included.
  • Typical timings: one appraisal preparation took 27 s. A full end-to-end test from new prospect to Exit runs in about 8 s on the mock provider.

Quality & evidence

555 automated tests

Offline, on the mock LLM with isolated config and storage. They cover the agent framework, field model, intake, reconciliation, workflow parity, templates and characterization snapshots of the CAM pipeline and API.

Golden extraction set

A fictional prospect with 7 documents and 23 expected values. 100% precision, and every value cites its page. 22 of 23 are found; the PAN on a scanned card needs a vision model and is reported, not guessed.

End-to-end journey

One test drives a new prospect from its documents through all 31 steps to Exit. It asserts the agent-populated domains, the confirmed fields and the MIS agent metrics.
