Technical · agent orchestration

How the agents are orchestrated

What starts the agents, which agent is in charge, who hands work to whom, and how a run ends: from the moment someone signs in to the verify queue they see.

1 · Sign-in2 · The cast3 · Triggers 4 · Hand-offs5 · How it ends6 · Across the journey

1 · What happens when someone signs in

Signing in does not start any agent. Agents are started by work on an application, not by a user's presence.

1
Sign-in person

POST /api/los/session creates a session for the chosen user and role. The token is sent on every call as X-LOS-Session.

2
Dashboard and copilot digest rules

The dashboard loads the user's queue. The copilot's rule-based planner ranks each item's next best action (SLA breaches first). This is a read: no agent runs and nothing is written.

3
The user opens an application person

The step card shows the step, the actions, and the Prepared by agents, verified by you card. It shows whether agents have prepared this step and offers Prepare with agents to the step holder.

4
A trigger fires orchestrator

Creating a prospect from documents, clicking Prepare with agents, running the credit assessment or correcting an engine input starts an orchestrated run in the background (§3).

2 · The cast: master agents and workers

There are two levels of command. The Preparation Orchestrator is the master agent for an application step. It picks a playbook and runs it as a graph. One of its workers, the credit case, has its own master: the CAM SuperAgent, which runs the seven credit-pipeline agents.

Every trigger is an action a person takes. The orchestrator then runs in the background, and the screen follows its lanes.

Guard rails on starting. Only the holder of the current step can trigger a preparation. Only one preparation and one credit run can be in progress per application; a second click is refused with already being prepared. Login, opening a page and the dashboard digest never start a run.

4 · Who hands off to whom

Hand-offs are not chat messages between agents. Each worker returns its result into the graph's shared context, keyed by its name. The graph starts the next worker once the results it requires are in. Work that has no dependency runs at the same time.

5 · How a run ends

When everything succeeds

  1. The last node finishes and the graph joins its results by name. The output does not depend on finishing order.
  2. The single writer takes the application lock, merges, materialises and saves once, with one audit event.
  3. The Orchestrator records application_prepared, with the lanes, durations and peak parallelism, and marks the job done.
  4. The screen stops showing Agents preparing… and opens the verify queue.
  5. The agents' part is over. The person verifies and takes the step's decision. The next step's agents start only when its holder triggers them.

When something fails

  • A failed lane, such as one check or one document, is marked unavailable. The other lanes still complete and are written.
  • A failure in something others require, such as no credit case, skips its dependants. The job ends failed with the reason, which the screen shows as Preparation failed: ….
  • An LLM that is down or set to mock is not fatal. Pattern extraction and deterministic drafts still run; scanned pages are reported as unread.
  • Nothing partial is written outside the single writer, so a failed run never leaves half-merged fields.

In one line: a person's action triggers the Preparation Orchestrator (master), which runs a playbook graph of parallel workers, including the CAM SuperAgent when a credit case is needed. The critic checks their proposals and one single writer saves them. The run ends in a verify queue, and a person takes the decision that moves the application on.
